# Development Notes

本复盘按三类证据写作：个人经历由本人说明；程序行为由保存源码确认；前期报告中的风险只代表设计讨论。没有实测或可靠记录的改进，不写成已解决的现场问题。

## 1. Mechanical design vs real-world constraints

前期夹爪风险报告和设计检查清单讨论了机构重量、重心、前伸、支撑刚性、夹持摩擦、线束和维护等取舍。它们说明机械方案需要考虑整车运动与执行机构的相互影响，尚不能证明某项风险实际发生。

| 设计问题 | 已有材料支持的讨论 | 当前记录缺口 |
| --- | --- | --- |
| 重量 | 末端增重会增加升降和结构负担，是早期选型考虑之一 | 没有整车/末端称重与迭代对比 |
| 重心 | 前伸和升降高度被列入稳定性风险 | 没有实物重心测量或倾覆测试结果 |
| 实际阻力 | 摩擦夹持与升降承载被讨论；不能只凭几何设计估计全部负载 | 没有导轨阻力、电流/扭矩与负载记录 |
| 理论与装配差异 | CAD、夹爪和升降方案有多个版本 | 未锁定各 CAD 与实物的对应关系，不能给出改进百分比 |

可保留的个人经验是：结构方案、SolidWorks 建模与装配调试需要相互校核。公开复盘若补充一次具体修改，应同时给出原问题、本人参与、对应版本、验证条件和实际结果；当前不补写“减重后更稳定”等未证实结果。

## 2. Transition from mechanical to software

根据本人经历说明，早期主要参与机械方案调研、执行机构、SolidWorks 结构和装配调试。随着项目需求变化，开始学习 Python、Raspberry Pi、OpenCV 与控制逻辑，并参与循迹、视觉定位、任务流程和整车联调。

软件栈中的任务、底盘、视觉、舵机接口为这段转向提供了具体学习材料：定位函数的返回值决定抓取是否继续，循迹和视觉各有状态，执行器还涉及等待、读回和并发时序。源码不能确定全部作者；这段成长不等于本人负责所有算法。

## 3. Real robot debugging

| 主题 | 保存代码可确认的处理 | 未证明的结果 |
| --- | --- | --- |
| 通信与设备节点 | `serial_ports.py` 先查稳定串口标识再回退；视觉客户端有健康检查、陈旧帧和串口错误路径 | 比赛当天每次异常的原因、修复操作和恢复结果 |
| 硬件连接 | GPIO、舵机 ID、相机和底盘串口均依赖实物对应 | 完整接线记录仍缺；下节通信线未接经历来自本人回忆，不由静态代码证明 |

## A Personal Debugging Case

**问题。** 这是我的个人经历记录。当时团队算法进度仍主要停留在循迹，机器人走不直的问题使后续任务联调难以推进。我原本主要负责机械，对树莓派和控制代码都还不熟悉，需要先理解车体、传感器和底盘指令之间的关系。

**判断。** 我提出增加前后双循迹传感器，通过前后两处线路信息改善方向判断：单看一处偏差，不容易区分车体整体偏离线路与车身方向偏斜。这是我参与提出的方案，不代表双排循迹原理或整个控制系统由我独创。

**排查。** 周末算法、电控成员无法到场后，我开始自己接触 Raspberry Pi，检查后循迹接线、摄像头位置并尝试视觉调试。排查底盘不响应时，发现主板与 Raspberry Pi 的通信线此前没有连接。这让我认识到，看到机器人不动，不能直接把原因归给算法；应沿供电、连接、设备识别、通信到控制输出逐层检查。

**修改。** 后续我参与编写和调整基础循迹控制函数，把前后线路信息与车体纠偏联系起来，并继续参与整车联调。现有记录不足以把每个参数或每行实现精确归为我的独立修改，也不能据此声称我独立完成了整个循迹系统。

**验证。** 我持续参与真机调试，但目前没有可公开的前后对比日志、偏差曲线或重复试验记录。因此只记录实际参与，不写成已经彻底解决走不直，也不填写未经测量的效果提升。

**学到什么。** 这次经历让我从机械装配走向软硬件联合排查，开始建立从现象、假设、检查到验证的调试习惯。Git 仓库能展示保存的团队实现，不能证明每一行代码的具体作者；个人参与与程序行为应分别说明。
